The examples are small, complete programs: each page is one `main.ts` in
[voxolith/examples](https://github.com/voxolith/examples), running live at
[voxolith.github.io/examples/](/examples/). They all need a browser with WebGPU. Each page below
says what the example shows, links the live page and its source, points at the APIs it uses, and
lists the URL options it reads.

If you are new, read them in that order: each builds on ideas from the ones before. The
[tutorial](/docs/tutorial/) walks through most of the same ground one step at a time.

## Running them locally

```sh
git clone https://github.com/voxolith/examples
```

Clone it into a workspace with the renderer, engine and generators, as in
[Installation](/docs/getting-started/installation/), add `"examples"` to the workspace list, then:

```sh
bun install
bun run --cwd examples dev
```

Open the `https://localhost:5173` URL and pick an example from the landing page.

## The Options panel

Every option a page takes in its URL can also be changed on the page. The HUD's Options button
opens a panel (a popover under the bar on a desktop, a bottom sheet on a narrow or touch screen)
with one control per option. What the page can change while it runs (the weather, the time of
day, a render scale) applies at once; the rest are marked "changed" and applied together by the
panel's "Apply and reload" button, and "Defaults" clears them all. Either way the panel rewrites
the query string, leaving out any value equal to its default on that device, so the address bar
always holds a link to what you see. Each example's page says which of its options apply at once.
Beside its own options, every panel has the same [renderer options](#renderer-options): quality,
temporal accumulation, the traced fraction, reflections, a fixed render scale and a debug view.
hello-vox, orbit and minecraft-region have only those. Switches meant for tools
(`?e2e` and a few per page) work in the URL only. A toggle is on as `?key` or `?key=1` and off as
`?key=0`; a number outside its range is clamped. Each page declares its options once, in its
`main.ts`, through [`src/shared/options.ts`](https://github.com/voxolith/examples/blob/main/src/shared/options.ts).

### Renderer options

Every page with a panel carries the renderer's own knobs under the same names, so any scene can
be tried at another quality without editing code:

| option | default | effect |
|---|---|---|
| `?quality=` | the page's (`medium` on a phone, `low` on a CPU adapter) | `low`, `medium` or `high`: the renderer's [preset](/docs/renderer/quality-and-performance/) |
| `?temporal` | off (on, on a phone) | [temporal accumulation](/docs/renderer/quality-and-performance/#temporal-accumulation) of shadows and ambient occlusion; nothing to accumulate on `low` |
| `?upscale=` | 1 (0 on a phone) | with temporal on: the fraction of the output size that is traced, up to 1 ([temporal upscaling](/docs/renderer/quality-and-performance/#temporal-upscaling)); 0 adapts it to the frame time, between 0.35 and 1 |
| `?reflections=0` | on (off on a phone) | off compiles out the secondary rays of water, metal and glass |
| `?renderScale=` | 0 | a fixed render scale up to 2; 0 leaves it to the page, adaptive where it uses `makePerf` |
| `?debug=` | | `10`: how many steps each primary ray took; `1`: the walk without empty-space skipping |
| `?perf` | | the page's performance overlay; on a phone, or wherever the traced fraction adapts, also a HUD line with the fps, the traced fraction and the GPU time |
| `?full` | | on a phone: the desktop settings (shown only on a device that gets the phone profile) |

The first six apply at once on every page; only on temporal does `?quality=` reload. `?perf` and
`?full` reload. A phone's defaults are the examples' [phone profile](/docs/manual/mobile-and-pwa/#the-examples-phone-profile); a CPU adapter
never gets it. The instances page has an `?upscale=` of its own (scaled copies), so it lacks the
shared one, and the bench, which measures, takes no phone profile and no `?upscale=0`. A page's
table lists these only where its defaults differ.

## Common URL options

Most examples read a few options of the same name (`?perf` is in the panel as "Performance overlay"; the other two are URL only):

| option | effect |
|---|---|
| `?diag` | show the adapter, the 3D texture limit and the storage binding limit in the page |
| `?perf` | where the example uses `makePerf`: show the frame-time and render-scale overlay; all but the bench also log the [load timeline](/docs/manual/loading-screens/#measuring) to the console, with the load time and "first frame at X s" in the overlay's label |
| `?e2e` | expose test hooks on `window` for the end-to-end input checks; not for normal use |

Every page also shows the same [loading screen](/docs/manual/loading-screens/#the-examples-loading-screen) while it loads: one row per step the page lists and an overall bar, then a corner pill for anything that continues in the background. A load that fails says so on that screen.

GPU validation errors and a lost device are shown in the page too, since a phone has no console.

## Offline

After one visit online, every example page loads offline, including pages you never opened: a
service worker caches the whole build on the first visit (see
[Offline and installing](/docs/manual/offline-and-installing/)). Generated models come from the
IndexedDB model cache, or are generated again in the browser, and the pages with instanced scenery
read their models' encodings and static bakes from a second IndexedDB cache, the
[scene cache](/docs/manual/managing-loading/#caching-encodings-and-bakes) (`voxolith-scene`, up to
2.5 GiB, least recently used out first), or compute them again. Both caps are sized to what the
pages stored at every scale when they went up to 100 voxels per metre (106 MB of models, 1816 MB
of encodings and bakes, measured). With
the caches, a coarse first stage and the ground filled on workers, a warm first frame of
nightwood at 50 voxels per metre is 0.5 s, where it was 6.6 s with the model cache alone
(measured; at 100, which the pages offered then, 1.0 s against 30.8 s). The examples only cache; they are not an installable app. A new deploy takes
over quietly and runs on the next load, and a deploy that changed a worker's code starts its cache
cold once, since each is salted by its worker's hashed URL. The dev server caches nothing. A
production build served from `localhost` keeps the model and scene caches but registers no service
worker, so it does not work offline there.

## Apps

Larger programs built on the same packages, each in its own repository:

- **[Viewer](/viewer/)**: open MagicaVoxel `.vox` files and Minecraft `.mca` regions, or build
  models from the generators and share them as codes. Installable, and it works offline after
  one visit, including every sample you have opened. [Source](https://github.com/voxolith/viewer)
- **[Demolition Shot](/demolition-shot/)**: aim, release, watch it crumble. A mobile demolition
  game and installable PWA, the engine's showcase. [Source](https://github.com/voxolith/demolition-shot)
- **[Editor](/editor/)**: a voxel editor, in its early days. Installable, and it opens offline
  after one visit. [Source](https://github.com/voxolith/editor)
