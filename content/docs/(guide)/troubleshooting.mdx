---
title: Troubleshooting
description: Fixes for WebGPU missing or slow, software adapters, lost devices, HTTPS on phones, blank canvases, share codes, big worlds on phones, loading text that does not update, a model or scene cache that stays cold and an app that does not load offline.
---

Most problems with a Voxolith page come down to WebGPU: whether the browser offers it, on which
adapter, and in what context. The examples append `?diag` to show what the page got (adapter,
3D texture limit, storage binding size), and they print GPU errors in the page, since a phone
has no console to read them in.

<Accordions type="multiple">

<Accordion id="webgpu-unsupported" title="&quot;WebGPU is not available in this browser&quot;">

`initGpu` throws a `WebGPUUnsupportedError` when `navigator.gpu` is missing, and
`showUnsupportedScreen` shows its message. Check the browser:

| browser | WebGPU |
|---|---|
| Chrome, Edge | on by default on Windows, macOS, ChromeOS and Android |
| Chrome on Linux | may need `chrome://flags/#enable-unsafe-webgpu`; see the next entry for speed |
| Safari | Safari 26 or newer, on macOS, iOS and iPadOS |
| Firefox | only where your version enables WebGPU (`dom.webgpu.enabled` in `about:config`) |

"No suitable GPU adapter was found" means the API exists but the browser would not give out an
adapter: the GPU is blocklisted, or hardware acceleration is off in the browser's settings.
`chrome://gpu` shows what Chrome decided and why.

If the message instead says the page "isn't a secure context", see
[HTTPS on phones](#https-on-phones) below.

</Accordion>

<Accordion id="linux-chrome-slow" title="Chrome on Linux is slow">

On Linux, Chrome's WebGPU runs much faster with Vulkan. The obvious fix, turning on
`chrome://flags/#enable-vulkan`, has a cost: it changes how video frames reach the screen for
the whole browser, and camera feeds in video calls (Meet, for one) can go white.

Instead, run a second Chrome just for development, with Vulkan enabled and its own profile
directory:

```sh
google-chrome --user-data-dir="$HOME/.cache/voxolith/chrome-dev" --enable-features=Vulkan https://localhost:5173/
```

It must be `--user-data-dir`, not `--profile-directory`: a second profile of the same user data
directory shares the running browser process and its GPU setup, so the flag would not apply. A
separate directory is a separate browser, and your everyday Chrome is untouched.

Add `--ozone-platform-hint=auto` to run natively on Wayland rather than through XWayland. The dev
server's certificate is self-signed, so this browser shows a warning for it once, like any other.

</Accordion>

<Accordion id="software-adapter" title="Very low frame rate, and the adapter is SwiftShader or llvmpipe">

The browser has fallen back to a CPU implementation of WebGPU. It works, but at a few frames a
second. `initGpu` detects this and sets `gpu.software` (it matches SwiftShader, llvmpipe,
lavapipe, softpipe and fallback adapters), and logs it to the console.

In your app, react to it:

```ts
renderer.setQuality(gpu.software ? "low" : "medium");
const perf = makePerf({ enabled: false, scale: gpu.renderScale, minScale: gpu.software ? 0.25 : 0.4 });
if (gpu.software) console.warn("Software WebGPU adapter: expect a low frame rate.");
```

and tell the player too, in the page.

The Low preset turns off shadows and ambient occlusion and halves the ray steps; a lower
`minScale` lets the adaptive resolution go further down. To get the real GPU back, check
`chrome://gpu` for why it was not used (often a blocklisted driver, or hardware acceleration
turned off).

</Accordion>

<Accordion id="device-lost" title="The picture freezes, or &quot;device lost&quot; appears">

The GPU device was lost: the driver reset after a frame took too long, the GPU ran out of
memory, the driver crashed, or a phone reclaimed the GPU from a background tab. The renderer
does not recover by itself; everything on that device is gone.

- Listen for it and tell the player, rather than showing a frozen image:

  ```ts
  gpu.device.lost.then((info) => {
    if (info.reason === "destroyed") return; // you called destroy() yourself
    document.getElementById("status")!.textContent = `GPU device lost: ${info.message || info.reason}. Reload to continue.`;
  });
  ```

  To recover without a reload, call `initGpu` again and rebuild the renderer and the world.
- If it happens on every load, the page is asking too much of the GPU. Lower the quality preset
  (fewer `maxSteps` and `shadowSteps`), the render scale, or the size of the world; a single
  very long frame is what triggers a driver reset.
- A lost device right after `createRenderer` or a large `edit` usually means memory. `?diag` in
  the examples shows the storage binding limit the device was granted.

</Accordion>

<Accordion id="https-on-phones" title="Works on the laptop, &quot;not a secure context&quot; on the phone">

WebGPU exists only in a secure context: HTTPS, or `http://localhost`. A phone opening the dev
server at `http://192.168.1.20:5173` is neither, so `navigator.gpu` is simply absent and
`initGpu` says the page "isn't a secure context".

Serve the dev server over HTTPS with `@vitejs/plugin-basic-ssl` and listen on the LAN:

```ts title="vite.config.ts"
import basicSsl from "@vitejs/plugin-basic-ssl";

export default defineConfig({
  plugins: [basicSsl()],
  server: { host: true },
});
```

Open the `https://192.168...` network URL Vite prints and accept the certificate warning once.
A deployed site on GitHub Pages is HTTPS already. `vite preview` on `localhost` is a secure
context without HTTPS, but not from another device.

</Accordion>

<Accordion id="blank-canvas" title="The page loads but the canvas is blank">

In rough order of likelihood:

1. **No frame was requested.** With `makeFrameLoop` not in continuous mode, nothing renders
   until you call `loop.invalidate()`. Call it once after setup, pass the loop to
   `createInput(canvas, { loop })`, and use `observeResize(canvas, loop)`.
2. **The canvas has no size.** It needs a CSS size (for example `position: fixed; inset: 0` or
   `width: 100%; height: 100%`), and `resizeToDisplay(gpu)` in the render callback to match its
   backing store to it.
3. **The world is outside the clip bounds.** A renderer made from dense `data` clips rays to the
   occupied box it found at construction. If you add voxels outside that box later, or start
   from no `data` and fill the world with `edit`, call
   `renderer.setClipBounds([0, 0, 0], [size.x - 1, size.y - 1, size.z - 1])`.
4. **The camera sees nothing.** It is inside the ground, below the world, or facing away. Log
   `camPos` and try a camera well above the middle of the world looking down.
5. **Lighting is missing.** Every frame needs the lighting and sky fields as well as the camera;
   spread `timeOfDay(...)` (or `atmosphereFrame(...)`) into `render`.
6. **A GPU error.** Look in the console for validation errors, or use the pattern in the
   examples' `src/shared/boot.ts`: listen for `uncapturederror` on `gpu.device` and show it.

The examples' `?selftest=1`, `2` and `3` (on orbit and world) draw debug bands that show which
stage of the voxel lookup works on the current GPU.

A CDP screenshot, not an in-page `drawImage`, is the way to check a WebGPU canvas from a test:
the canvas does not survive `drawImage` outside the frame that drew it, so an in-page readback
reports every page as blank.

</Accordion>

<Accordion id="minecraft-region" title="The minecraft-region example shows nothing">

That is expected until you give it a file: it bundles no world. Drop a region file
(`r.X.Z.mca`, from the `region/` folder of any Minecraft Java world) onto the page. The info line
says "building…" while it parses and reports the chunks and voxels when it is done. A region with
nothing near its middle 256 × 256 blocks shows little; try another one.

</Accordion>

<Accordion id="share-codes" title="A share code will not load, or builds a different model">

A share code is a generator id, its version, a seed and the values of its declared parameters,
packed into a short string. `decodeState` refuses a code rather than guess:

- **"Generator … is not registered"**: register the generators before decoding, for example
  `registerTreeGenerators()` from `@voxolith/gen-tree`, once at startup.
- **"Share code was made with different parameters"**: the generator's parameter list changed
  since the code was made (a parameter added, removed or re-stepped), so the same numbers would
  now mean something else. Rebuild the model in the build that made the code, or make a new code.
- **"Unsupported share code version"**: the string is not a share code, or was cut short when it
  was pasted.

A code carries only the parameters a generator declares, and values snap to each parameter's
step grid; anything else comes from the generator's defaults. A code decoded at the default 10
voxels per metre always rebuilds the same voxels; asking for a finer scale
(`{ voxelsPerMetre: 100 }`) builds the same design in more detail. See
[Share codes](/docs/generators/share-codes/).

</Accordion>

<Accordion id="big-worlds-on-phones" title="Big worlds on phones: the valley will not start, or crashes">

Phones have less GPU memory and smaller storage buffer bindings than desktops. On a desktop Radeon
the valley example holds about 126 MB of GPU memory at its desktop default of 50 voxels per metre,
560 MB at `?vpm=100` and 19 MB at 20. It therefore picks a lighter profile when it sees a
touch-only pointer, or a GPU whose largest storage binding is under 512 MiB: coarser voxels and a
smaller valley.

| setting | desktop | phone |
|---|---|---|
| voxels per metre (`?vpm=`) | 50 (2 cm) | 20 (5 cm) |
| valley size (`?scale=`) | 4 × 4 tiles | 2 × 2 tiles |
| models per species (`?variants=`) | 3 | 1 |
| rats (`?rats=`) | 60, at 100 only | 20, at 100 only |
| streamed radius (`?radius=`) | 24 m | 16 m |
| quality preset | Medium | Low |

Rats are built only at a scale where they come out at their real size, which is 100 voxels per
metre; at 20 or 50 the HUD says "rats at 1 cm". `?full` asks for the desktop settings anyway, and
each setting can be given on its own. If the phone profile still fails, lower `?scale=` and
`?radius=` further and stay at 20 voxels per metre (the HUD's "Switch to 2 cm" button costs nearly
seven times the memory). The nightwood example uses the same test and the same scales.

The same approach works in your own app: read `gpu.limits.maxStorageBufferBindingSize` and
`matchMedia("(pointer: coarse)")` once at startup and size the world from them. See
[Mobile and PWA](/docs/manual/mobile-and-pwa/) and [Performance](/docs/manual/performance/).

</Accordion>

<Accordion id="loading-text-stuck" title="The loading text doesn't update during a step">

Load events are sent synchronously, from inside the step that reports them. When that step
blocks the main thread (uploading models, the static instance placement, a pipeline compile, a
layout of your own), the browser cannot repaint until it returns, so the `start` message and the
`end` reach the screen together, and the text seems stuck on the phase before.

Open the phase, let a frame paint, then run the step:

```ts
const scenery = load.task("scenery");
await new Promise((r) => requestAnimationFrame(() => setTimeout(r, 0)));
layer.commit();
scenery.end();
```

A single `await new Promise(requestAnimationFrame)` is not enough: the code after it still runs
before that frame is painted. See
[Loading screens](/docs/manual/loading-screens/#the-main-thread-stalls).

Two of those steps can stop blocking instead
([Managing loading](/docs/manual/managing-loading/)):

- **The model uploads and the static placement**: give the instance layer a scene worker
  (`makeInstanceLayer(renderer, { worker })`) and `await layer.commitAsync()`; `setStatic` then
  returns at once, and the page keeps painting while the models encode and the set bakes. With the
  older bake-only placement worker, uploading new models in `setStatic` still blocks, so keep the
  wait in front of that.
- **The pipeline compile**: without `prepare`, the first frame after loading stalls while the
  browser compiles the pipelines it uses, and that stall is not in the `pipelines` phase. Create
  the renderer with `deferPipelines: true` and `await renderer.prepare()` behind the loading
  screen: the compile then happens there, and `pipelines` measures it.

</Accordion>

<Accordion id="model-cache-cold" title="Every visit generates the models again">

The generator worker's model cache (`serveGenerators({ cache })`) should serve a second visit
without generating. When it does not, in order of likelihood:

- **It is a dev server.** The cache is meant to be off there (`import.meta.env.DEV ? undefined :
  "..."`), and a dev worker URL does not change with the code anyway.
- **Two worker scripts share one database name.** Opening the cache deletes the entries of any
  other worker script, so two workers (or two apps on one origin, as on GitHub Pages) with the
  same name delete each other's models. Give each worker script its own name.
- **The engine was just upgraded.** The cache database moved to version 2, which drops the
  older records once: the first visit after the upgrade is cold, the next ones are warm.
- **A new build.** The key is salted with the worker's hashed URL, so a new build starts cold by
  design.
- **The browser evicted it**, or it hit the quota or a `maxBytes` cap. Check with
  `openModelCacheControls(name)` and `usage()`, and see
  [Managing loading](/docs/manual/managing-loading/#the-model-cache) for phones. A cap smaller
  than what one session needs evicts the models of the scene just left; size it by
  [measuring](/docs/manual/managing-loading/#sizing-a-cap), and look for a
  [cap warning](#cache-cap-warning) in the console.

</Accordion>

<Accordion id="scene-cache-cold" title="Every visit encodes and bakes the scene again">

With `serveScene({ cache })`, a warm visit should read the static set's bake and the models'
encodings: the `placement` and `upload` phases then count their work as cached, and a warm
placement takes a fraction of a second. When they do not:

- **It is a dev server.** The scene cache is meant to be off there, like the model cache: the dev
  worker URL does not change with the code.
- **A cap evicted it.** A `maxBytes` evicts the least recently used entries after each write, and a
  result bigger than the cap is not kept at all (with a [warning](#cache-cap-warning), once). At
  100 voxels per metre one page stores hundreds of MB (the examples' valley 824 MB, both stages),
  so a small cap, or visiting several heavy pages, pushes the others out. Check with
  `openSceneCacheControls(name)` and `usage({ kind: "placement" })`, and
  [size the cap](/docs/manual/managing-loading/#sizing-a-cap) from what the scenes store.
- **A version bump or a new build.** Keys carry `ENCODED_MODEL_VERSION` and `PLACEMENT_BAKE_VERSION`,
  and are salted with the scene worker's hashed URL, so new renderer code starts cold once by design.
- **The encodings have no identity.** Without `modelKey` or `hashModels` on the layer, encodings are
  not cached (the bake still is). `pool.modelKey` knows only models the pool returned; a model you
  built or copied yourself needs `hashModels`.
- **The scene changed.** A bake is found by its whole input: any moved, added or removed instance,
  or a model whose voxels changed, is a new bake. A layout drawn from `Math.random()` or the clock
  never hits.
- **Shared database name.** The scene cache and the model cache (or two scene worker scripts) under
  one name delete each other's entries every time either opens it.
- **The writes were lost.** `destroy()` terminates a worker still running a job at once, and gives
  an idle one `closeTimeoutMs` (10 s) to finish its writes. A deflating cache (`compress: true`)
  after a big first visit can need longer: raise it, or keep the worker.

See [caching encodings and bakes](/docs/manual/managing-loading/#caching-encodings-and-bakes).

</Accordion>

<Accordion id="cache-cap-warning" title="A warning about maxBytes, or serveGenerators throws a RangeError">

The model and scene caches check their `maxBytes` when a worker opens them. The engine picks no
cap, so these are about a cap your game set:

- **`RangeError: ... maxBytes must be a positive, finite number`**, thrown by `serveGenerators` or
  `serveScene`: the cap is 0, negative, `NaN`, `Infinity` or not a number (a string from a
  settings file, say). Leave it out for no cap.
- **"maxBytes is ..., under 16 MiB"**: below
  [`CACHE_CAP_FLOOR`](/docs/engine/api/worker/variables/CACHE_CAP_FLOOR/). One refined model or
  bake is often bigger, so the cache keeps little. A cap in the wrong unit (MB where bytes were
  meant) lands here.
- **"above this origin's storage quota"**: the browser evicts before the cap is reached, so the
  cap never applies. Lower it, or ask for room with `navigator.storage.persist()`.
- **"an entry of ... is larger than maxBytes"**: that model or bake is not cached and is rebuilt
  on every visit. Raise the cap. It warns once; later ones are skipped silently.

Each warning comes once per cache, and each worker opens its own, so a pool of four workers may
print it four times. To size a cap, load the heaviest scenes once on a production build with no
cap, read `usage()` from `openModelCacheControls` and `openSceneCacheControls`, and add headroom:
see [sizing a cap](/docs/manual/managing-loading/#sizing-a-cap).

</Accordion>

<Accordion id="holes-in-the-first-view" title="The first view has holes in the ground, or the edge of the world shows">

A streamed world builds its chunks nearest first, and a page shown before they are in shows the
gaps. In order of likelihood:

- **The first picture does not wait for enough ground.** Wait for the ground around the camera
  before showing the page: `await world.whenReady(x, z, radius)` (or loop on `readyAround`), with a
  radius that covers what the first view sees. The examples call it the near-ground gate, `?near=`
  in metres: nightwood waits for 8 m (6 m left holes in its fog at 100 voxels per metre) and the
  valley for 18 m. A smaller gate is quicker and shows holes at the edge of the first view. See
  [ready around the camera](/docs/manual/managing-loading/#ready-around-the-camera).
- **The radius is tested at chunk centres.** A chunk whose centre is outside the radius but whose
  edge reaches into the view does not count. Add half a chunk's diagonal (`chunk * Math.SQRT1_2`).
- **`whenReady` never resolves.** It waits for what `focus` queued and `step` builds: focus on at
  least its radius around the same point, and keep calling `step` (from the frame loop, or a loop
  behind the loading screen).
- **A chunk failed to fill on a worker.** With `makeChunkedWorld({ fill })` a failed chunk stays
  empty, is reported to `onError` (by default `console.error`, "chunk ... failed to fill"), is not
  retried until it has been freed, and makes a `whenReady` over it reject. Look for the error in
  the console.
- **Holes after moving.** The world keeps building in `step`; a budget too small for the camera's
  speed lets the view outrun it. See [Streaming](/docs/manual/streaming/#costs).

</Accordion>

<Accordion id="not-offline" title="The app does not load offline">

An app built with `serviceWorker()` from `@voxolith/engine/vite` and registered with
`registerServiceWorker()` loads offline after one visit online. When it does not:

- **It is a dev server or localhost.** There is no worker on `vite dev` (the plugin runs on
  `vite build` only), and registration skips `localhost`, `127.0.0.1` and `[::1]`. To try it,
  build, run `vite preview` and pass `registerServiceWorker({ localhost: true })`.
- **The first visit had not finished.** The worker registers after the page's `load` event and
  then precaches; `onOfflineReady` says when that is done.
- **A public file is missing.** Files in `public/` are not in the bundle, so they are precached
  only when listed in `include`, and fetched data is cached only by a `runtime` rule or once it
  has been fetched.
- **The base is relative.** The worker's scope comes from Vite's `base`, which must be `/` or
  `/<repo>/`.
- **The page shows the old version after a deploy.** The page that was open keeps its code; the
  next load runs the new build, and `onUpdate` fires when the new worker has taken over.

See [Offline and installing](/docs/manual/offline-and-installing/).

</Accordion>
